# Mecanismos de seguridad

Al igual que en Apache HTTP Server, un servidor de aplicaciones como Tomcat requiere configurar mecanismos de **autenticación, autorización y protección de las comunicaciones**.

## Protección del panel de administración (Manager/Host Manager)

Tomcat incluye dos aplicaciones web de administración muy sensibles:

- **Manager**: permite desplegar, recargar y detener aplicaciones vía web.
- **Host Manager**: permite gestionar hosts virtuales.

Por defecto, su acceso está protegido mediante los usuarios definidos en `tomcat-users.xml`:

```xml
<tomcat-users>
    <role rolename="manager-gui"/>
    <role rolename="admin-gui"/>
    <user username="admin" password="ContraseñaSegura123!" roles="manager-gui,admin-gui"/>
</tomcat-users>
```

!!! danger "Nunca dejes el Manager accesible sin restricciones"
    El panel de administración de Tomcat es uno de los objetivos favoritos de los atacantes automatizados. Además de exigir usuario/contraseña, es recomendable **restringir el acceso por IP** (ver siguiente apartado) y **jamás** exponerlo directamente a internet sin protección adicional.

## Restricción de acceso por IP a aplicaciones sensibles

En el fichero `conf/Catalina/localhost/manager.xml` (o mediante un `context.xml` específico):

```xml
<Context antiResourceLocking="false" privileged="true">
  <Valve className="org.apache.catalina.valves.RemoteAddrValve"
         allow="127\.0\.0\.1|192\.168\.1\.\d+" />
</Context>
```

- **`RemoteAddrValve`**: *Valve* (interceptor) que filtra las peticiones según la IP de origen, permitiendo solo las que coincidan con la expresión regular indicada.

## Roles y autenticación basada en roles (declarativa)

Las aplicaciones Java EE pueden proteger rutas concretas declarando restricciones de seguridad en su propio `web.xml`:

```xml
<security-constraint>
    <web-resource-collection>
        <web-resource-name>Zona administración</web-resource-name>
        <url-pattern>/admin/*</url-pattern>
    </web-resource-collection>
    <auth-constraint>
        <role-name>ADMIN</role-name>
    </auth-constraint>
</security-constraint>

<login-config>
    <auth-method>BASIC</auth-method>
    <realm-name>Zona restringida</realm-name>
</login-config>
```

Esto es equivalente, a nivel de aplicación, a lo que hacíamos con `Require valid-user` en Apache HTTP Server, pero definido en la propia aplicación Java en lugar de en el servidor web.

## Configuración de HTTPS directamente en Tomcat

Aunque en producción se suele delegar HTTPS a Apache (como vimos en el tema de cooperación), Tomcat también puede gestionar HTTPS directamente mediante un conector SSL:

```xml
<Connector port="8443" protocol="org.apache.coyote.http11.Http11NioProtocol"
           maxThreads="150" SSLEnabled="true">
    <SSLHostConfig>
        <Certificate certificateKeystoreFile="conf/keystore.jks"
                     certificateKeystorePassword="cambia_esta_contraseña"
                     type="RSA" />
    </SSLHostConfig>
</Connector>
```

### Generar un almacén de claves (*keystore*) Java

```bash
keytool -genkeypair -alias tomcat -keyalg RSA -keysize 2048 \
  -keystore /opt/tomcat/conf/keystore.jks -validity 365
```

- **Keystore**: fichero que almacena claves y certificados en formato propio de Java (`.jks`), similar en concepto a los certificados `.crt`/`.key` de OpenSSL vistos con Apache.

## Buenas prácticas de seguridad en el servidor de aplicaciones

- Cambiar siempre las **contraseñas por defecto** del Manager y Host Manager.
- Eliminar las aplicaciones de ejemplo (`examples`, `docs`, `ROOT` por defecto) en entornos de producción.
- Mantener **Tomcat y la JVM actualizados** frente a vulnerabilidades conocidas.
- Ejecutar Tomcat con un **usuario sin privilegios** (nunca como `root`).
- Restringir el acceso a los puertos de administración (`8005`) y al conector AJP (`8009`) solo a `localhost` o a la red interna.
- Combinar la seguridad propia de Tomcat con la de Apache HTTP Server cuando cooperen entre sí (defensa en profundidad).
