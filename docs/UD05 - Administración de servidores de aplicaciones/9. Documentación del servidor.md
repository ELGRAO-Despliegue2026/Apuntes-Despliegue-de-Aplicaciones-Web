# Documentación del servidor

Como se vio en la UD05 (Documentación), toda administración de un servidor debe quedar documentada. En este apartado aplicamos esos conceptos específicamente a un **servidor de aplicaciones**.

## ¿Por qué documentar el servidor de aplicaciones?

- Permite que **otro administrador** (o tú mismo en el futuro) entienda rápidamente cómo está configurado el servidor.
- Facilita la **resolución de incidencias** al tener centralizada la información de versiones, rutas y configuraciones.
- Es necesaria para **auditorías de seguridad** y cumplimiento normativo.
- Sirve de base para automatizar despliegues (scripts, *Infrastructure as Code*).

## Contenido recomendado de la documentación

### 1. Información general del servidor

- Versión de Tomcat y de la JVM instaladas.
- Sistema operativo y versión.
- Ubicación de `CATALINA_HOME` y `CATALINA_BASE`.

```bash
/opt/tomcat/bin/version.sh
java -version
```

### 2. Configuración de conectores y puertos

| Puerto | Protocolo | Uso                           |
|--------|-----------|---------------------------------|
| 8080   | HTTP      | Acceso directo (normalmente solo interno) |
| 8009   | AJP       | Comunicación con Apache HTTP Server |
| 8443   | HTTPS     | Acceso cifrado directo (si aplica) |
| 8005   | -         | Puerto de administración/apagado  |

### 3. Aplicaciones desplegadas

| Aplicación | Ruta de contexto | Versión | Fecha de despliegue | Responsable |
|------------|--------------------|---------|------------------------|---------------|
| miapp      | `/miapp`           | 1.3.0   | 2024-10-01             | Carles        |

### 4. Usuarios y roles configurados

Documentar (sin incluir las contraseñas en texto plano en el propio documento) qué usuarios tienen acceso al Manager/Host Manager y con qué rol.

### 5. Mecanismos de seguridad aplicados

- Si el Manager está restringido por IP.
- Si se usa HTTPS directamente en Tomcat o delegado en Apache.
- Si el conector AJP está expuesto o restringido a `localhost`.

### 6. Procedimientos habituales

Es recomendable documentar los procedimientos paso a paso para las tareas más comunes:

```markdown
## Cómo desplegar una nueva versión de la aplicación

1. Generar el WAR: `jar -cvf miapp.war *`
2. Copiar el WAR al servidor: `scp miapp.war usuario@servidor:/tmp`
3. Desplegar vía Manager:
   curl -u admin:contraseña --upload-file /tmp/miapp.war \
     "http://localhost:8080/manager/text/deploy?path=/miapp&update=true"
4. Comprobar el log: tail -f /opt/tomcat/logs/catalina.out
5. Verificar funcionamiento: curl -I http://localhost:8080/miapp/
```

### 7. Recomendaciones de uso y mantenimiento

- Frecuencia recomendada de revisión de logs.
- Política de copias de seguridad (qué se respalda: `webapps/`, `conf/`, bases de datos asociadas).
- Plan de actualización de Tomcat/JVM.

## Dónde y cómo mantener esta documentación

Siguiendo lo visto en la unidad de documentación:

- Usar **Markdown** y un generador como **MkDocs**, versionado con **Git**, para mantener un histórico de cambios en la configuración documentada.
- Mantener la documentación en el **mismo repositorio** (o uno asociado) que el código de la aplicación, de forma que ambos evolucionen juntos.
- Revisar y actualizar la documentación **cada vez que se modifique la configuración** del servidor (nuevo conector, nuevo usuario, cambio de certificado...).

!!! tip
    Una plantilla sencilla de documentación de servidor, mantenida y actualizada, aporta mucho más valor que una documentación extensa pero desactualizada. Prioriza la **exactitud** sobre la extensión.
