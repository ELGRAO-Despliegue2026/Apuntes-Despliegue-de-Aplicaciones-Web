# Protocolos de Internet

Para que dos máquinas puedan comunicarse a través de internet es necesario que compartan un conjunto de reglas: los **protocolos**. En este apartado veremos cómo se organizan estos protocolos en capas y cómo se establece una conexión fiable antes de poder enviar ninguna petición web.

## El modelo TCP/IP

Las comunicaciones en internet se organizan en una pila de capas, donde cada una se apoya en la anterior:

```mermaid
graph TD
    A[Capa de Aplicación - HTTP, HTTPS, FTP, SMTP...] --> B[Capa de Transporte - TCP, UDP]
    B --> C[Capa de Red - IP]
    C --> D[Capa de Enlace/Física]
```

- **Capa de aplicación**: protocolos que usan directamente las aplicaciones (HTTP, HTTPS, FTP, SMTP, DNS...).
- **Capa de transporte**: garantiza (o no) la entrega fiable de los datos. Los dos protocolos principales son **TCP** (fiable, orientado a conexión) y **UDP** (más rápido, sin garantías).
- **Capa de red**: encargada del direccionamiento mediante **IP** (direcciones IPv4/IPv6) y el enrutamiento entre redes.
- **Capa de enlace/física**: transmisión de los bits sobre el medio físico (cable, fibra, WiFi...).

## TCP vs UDP

| Característica       | TCP                          | UDP                        |
|------------------------|-------------------------------|-------------------------------|
| Orientado a conexión    | Sí                             | No                             |
| Fiabilidad              | Garantiza la entrega y el orden | No garantiza nada              |
| Velocidad               | Más lento (por el control)    | Más rápido                     |
| Uso típico              | HTTP, HTTPS, FTP, SSH, email  | Streaming, VoIP, DNS, juegos online |

HTTP y HTTPS, los protocolos en los que nos centraremos en esta unidad, funcionan siempre sobre **TCP**, ya que necesitan garantías de que los datos lleguen completos y en orden.

## Direcciones IP y puertos

Cada equipo conectado a una red dispone de una **dirección IP** que lo identifica. Además, cada servicio que se ejecuta en ese equipo escucha en un **puerto** concreto:

- Puerto **80**: HTTP (sin cifrar).
- Puerto **443**: HTTPS (cifrado).
- Puerto **22**: SSH.
- Puerto **21**: FTP.

Una conexión queda identificada de forma única mediante el conjunto `(IP origen, puerto origen, IP destino, puerto destino, protocolo)`.

## Establecimiento de una conexión TCP: el saludo de tres vías (*3-way handshake*)

Antes de poder enviar ninguna petición HTTP, el cliente y el servidor deben establecer primero una **conexión TCP fiable**, mediante el intercambio de tres mensajes:

```mermaid
sequenceDiagram
    participant C as Cliente
    participant S as Servidor

    C->>S: SYN (quiero iniciar una conexión, nº secuencia=X)
    S-->>C: SYN-ACK (de acuerdo, nº secuencia=Y, confirmo tu X+1)
    C->>S: ACK (confirmo tu Y+1, comenzamos)
    Note over C,S: Conexión TCP establecida
```

- **SYN** (*synchronize*): el cliente indica al servidor que quiere iniciar una conexión y le propone un número de secuencia inicial.
- **SYN-ACK**: el servidor confirma (*ACK*) la petición del cliente y, a su vez, propone su propio número de secuencia (*SYN*).
- **ACK** (*acknowledge*): el cliente confirma la respuesta del servidor. A partir de aquí la conexión queda establecida y pueden empezar a intercambiarse datos.

### ¿Qué protección aporta TCP mediante los números de secuencia?

Cada paquete TCP incluye un **número de secuencia**, que permite:

- Detectar y descartar paquetes **duplicados**.
- Reordenar paquetes que lleguen **desordenados** por la red.
- Detectar paquetes **inyectados por un atacante externo** a la conexión, ya que este desconoce el número de secuencia acordado durante el *handshake* y sus paquetes serían rechazados.

Por tanto, el número de secuencia no solo garantiza la entrega ordenada, sino que también aporta una primera barrera de protección frente a ataques externos a la red que intenten interferir en una conexión ya establecida.

## Cierre de una conexión TCP

Una vez terminada la comunicación, la conexión se cierra también mediante un intercambio de mensajes (*4-way handshake* o terminación con `FIN`/`ACK`):

```mermaid
sequenceDiagram
    participant C as Cliente
    participant S as Servidor

    C->>S: FIN (quiero cerrar la conexión)
    S-->>C: ACK (de acuerdo, confirmo)
    S-->>C: FIN (yo también cierro)
    C->>S: ACK (confirmo el cierre)
    Note over C,S: Conexión TCP cerrada
```

## DNS: traduciendo nombres a direcciones IP

Los humanos no recordamos direcciones IP, sino nombres de dominio (`www.ejemplo.com`). El protocolo **DNS (Domain Name System)** se encarga de traducir esos nombres a direcciones IP:

```mermaid
sequenceDiagram
    participant C as Cliente
    participant DNS as Servidor DNS
    participant S as Servidor Web

    C->>DNS: ¿Cuál es la IP de www.ejemplo.com?
    DNS-->>C: 93.184.216.34
    C->>S: Conexión TCP + petición HTTP a 93.184.216.34
```

Este proceso ocurre **antes** del *3-way handshake*, ya que el cliente necesita conocer la IP de destino para poder iniciar la conexión TCP.

## Jerarquía de dominios y orden de resolución DNS

Un nombre de dominio se organiza de forma jerárquica, de derecha a izquierda:

```text
www.wikipedia.org
 │      │      └── Dominio de nivel superior (TLD): .org
 │      └────────── Dominio de segundo nivel: wikipedia
 └───────────────── Subdominio: www
```

El **dominio de nivel superior (TLD)** es la parte final (`.org`, `.com`, `.es`...), gestionado por una entidad específica para esa extensión.

Cuando un cliente necesita resolver un dominio, el proceso sigue este orden, deteniéndose en cuanto encuentra una respuesta:

1. **Caché del navegador**: comprueba si ya ha resuelto ese dominio recientemente.
2. **Caché DNS del sistema operativo**: el propio SO mantiene su propia caché de resoluciones recientes.
3. **Archivo local de mapeo de IPs** (`/etc/hosts` en Linux): fichero estático donde se pueden definir resoluciones manuales.
4. **Servidor DNS externo configurado** (por ejemplo, `8.8.8.8` de Google): se envía la consulta a este servidor.
5. **Búsqueda recursiva**: si el servidor DNS externo no la tiene en caché, realiza una búsqueda recursiva, preguntando en orden al **servidor raíz**, después al servidor del **TLD** correspondiente (`.org`, `.com`...) y finalmente al **servidor autoritativo** del dominio, que es quien conoce la IP real.

```mermaid
graph TD
    A[Caché del navegador] --> B[Caché DNS del SO]
    B --> C[Archivo /etc/hosts]
    C --> D[Servidor DNS externo]
    D --> E[Servidor raíz]
    E --> F[Servidor TLD .org/.com...]
    F --> G[Servidor autoritativo del dominio]
```

## Resumen del flujo completo

```mermaid
graph LR
    A[1. Resolución DNS] --> B[2. 3-way handshake TCP]
    B --> C[3. Petición/Respuesta HTTP]
    C --> D[4. Cierre de la conexión TCP]
```
