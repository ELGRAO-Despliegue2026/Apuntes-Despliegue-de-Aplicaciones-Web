    Accesibilidad y seguridad de la documentación

    Más allá de generar y almacenar la documentación en un sistema de control de versiones, es necesario garantizar que esté disponible para quien la necesite y protegida frente a accesos o modificaciones no autorizadas.

    Accesibilidad

    Permisos y visibilidad de repositorios

    • Repositorios públicos: accesibles a cualquier usuario, adecuados para documentación de proyectos de código abierto.
    • Repositorios privados: solo accesibles a los miembros del equipo o a invitados autorizados.
    • Grupos y equipos: GitHub/GitLab permiten organizar usuarios en equipos y asignar permisos (lectura, escritura, administración) de forma granular.

    Publicación de la documentación

    Para garantizar que la documentación sea fácilmente accesible, se suele publicar automáticamente como sitio web estático:

    • GitHub Pages
    • GitLab Pages
    • Read the Docs

    Ejemplo de despliegue automático de MkDocs a GitHub Pages:

    pip install mkdocs
mkdocs gh-deploy

    Accesibilidad web (a11y)

    Cuando la documentación se publica como sitio web, conviene aplicar buenas prácticas de accesibilidad:

    • Uso correcto de encabezados (h1, h2...).
    • Texto alternativo en imágenes.
    • Contraste de color adecuado.
    • Navegación posible mediante teclado.

    Seguridad

    Copias de seguridad

    Al estar versionada en Git, la documentación dispone de un historial completo, pero conviene además:

    • Tener repositorios remotos redundantes (por ejemplo, un mirror).
    • Realizar copias de seguridad periódicas del servidor Git si es autoalojado (git bundle, git clone --mirror).

    Autenticación y control de acceso

    • Uso de claves SSH en lugar de contraseñas para autenticar el acceso a los repositorios.
    • Activación de autenticación en dos factores (2FA) en las cuentas de las plataformas (GitHub, GitLab).
    • Uso de tokens de acceso personal con permisos limitados en lugar de contraseñas en integraciones automatizadas.
    # Ejemplo de clonado usando SSH
git clone git@github.com:usuario/mi-proyecto.git

    Protección de ramas

    Las plataformas permiten proteger ramas importantes (como main) exigiendo:

    • Revisión obligatoria antes de fusionar (pull/merge request approval).
    • Superación de comprobaciones automáticas (CI) antes de poder fusionar.
    • Prohibición de push directo sin revisión.

    Integridad del historial

    Git garantiza la integridad del historial mediante el uso de hashes SHA-1/SHA-256 para cada commit, lo que permite detectar si el contenido ha sido alterado.

    Firmado de commits

    git config --global commit.gpgsign true
git commit -S -m "Commit firmado digitalmente"

    El firmado de commits con GPG permite verificar que un commit realmente proviene del autor que dice ser.

    Resumen de buenas prácticas

    • Definir claramente quién puede leer y quién puede escribir la documentación.
    • Publicar la documentación en un sitio accesible y navegable.
    • Proteger las ramas principales frente a cambios no revisados.
    • Usar SSH/2FA/tokens en lugar de contraseñas simples.
    • Mantener copias de seguridad del repositorio.
